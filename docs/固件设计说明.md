## 0. 这份文档解决什么

`firmware/README.md` 讲**怎么用**，本文讲**为什么这么设计**——尤其是几个必须做取舍的地方。

---

## 1. 核心约束：键盘是「无状态」的

这是整个固件设计里最重要的一条认知，它决定了哪些功能能做、哪些必须交给上位机。

**键盘只能发按键，收不到任何状态。** 它不知道：

- 当前 Claude Code 处于哪个权限档位（plan / default / acceptEdits / auto）
- 当前用的是哪个模型（Opus / Sonnet）
- 是否有审批弹窗正在等待

所以 PRD 里那些「听起来键盘自己能做」的操作，实际上分两类：

| 类型 | 例子 | 实现方式 |
|---|---|---|
| **纯输出** | 单击发 `Shift+Tab`、发 `/model`、发 `Esc` | ✅ 键盘独立完成 |
| **依赖状态** | 长按「复位到 default」、长按「循环切换模型」 | ❌ 键盘只发**信号**，上位机执行 |

### 1.1 为什么「复位到 default」不能由键盘做

直觉方案是：长按就连续发 `Shift+Tab` 直到转回 default。但**转几圈才回到 default 是不确定的**：

- 用户在键盘外按过 `Shift+Tab`
- Claude Code 自己切换过（比如 plan 批准后进入 auto）
- 循环里有 4 档，从哪一档出发都是未知的

所以键盘只能发一个「请求复位」的信号，由**读取终端状态栏的上位机**执行真正的复位——因为只有上位机知道当前在哪一档。

### 1.2 信号怎么发

用 `Ctrl+Alt+Shift+F13` / `F14` 这类**极难误触**的组合：

```dts
m_perm_reset:  &kp LC(LA(LS(F13)))
m_model_cycle: &kp LC(LA(LS(F14)))
```

为什么用 F13/F14：它们在 HID 协议里是合法键码（0x68 起），但普通键盘没有这些键，所以**不会被误触发**，也不会与任何软件的快捷键冲突。上位机监听这两个键即可。

## 2. 矩阵设计

### 2.1 为什么是 3 行 × 6 列

物理布局是三行五列 11 键，但矩阵多了一列——**第 6 列专门给审批拨杆**。

好处：拨杆被当作一个普通按键处理，不需要写自定义驱动就能被固件读到。拨到 ON 时它表现为「持续按下」，OFF 时释放。

```
        列1    列2    列3    列4    列5    列6
行1     访问    ↑     模型   命令行  停止   审批拨杆   ← 6 个
行2      ←      ↓      →     回车     —      —        ← 4 个
行3     空格    —      —      —     语音     —        ← 2 个
```

12 个交点全部用上，无浪费。

### 2.2 大键的并联接法

回车（2u）和空格（4u）在定位板上分别开了 2 个和 3 个轴孔（解决长键翘曲）。这些轴体在**电气上并联**到同一个矩阵交点：

- 回车：两个轴都接 `(行2, 列4)`
- 空格：三个轴都接 `(行3, 列1)`

**PCB 设计时必须把这些焊盘接到同一条行线/列线**，否则会出现两个独立的键位。

### 2.3 二极管方向

`diode-direction = "col2row"`，即二极管从列线指向行线，行线用 `GPIO_PULL_DOWN`。

审批拨杆虽然是开关不是轴体，**建议也串一只 1N4148**——否则拨杆 ON 时与其他键同按可能产生鬼影。

## 3. 手势实现

ZMK 没有现成的「单击 A、双击 B、长按 C」三合一行为，需要用**行为嵌套**组合出来。

### 3.1 嵌套结构总览

| 键位 | 外层（hold-tap） | 内层（tap-dance） |
|---|---|---|
| 停止 | 长按 = 退出会话 | 单击 = Esc，双击 = Ctrl+C |
| 语音 | 按住 = Space | 单击 = 无，双击 = /voice |

其余键位只用到一层：

| 键位 | hold-tap |
|---|---|
| 访问等级 | 长按 = 复位信号 / 单击 = Shift+Tab |
| 模型 | 长按 = 循环信号 / 单击 = /model |
| 命令行 | 长按 = `@` / 单击 = `/` |
| 空格 | 长按 = Tab / 单击 = Space |
| 回车 | 仅 tap-dance（单击 Enter，双击 Shift+Enter） |

### 3.2 长按侧为什么用「宏」而不是「按键」

以命令行键为例：长按要输出 `@`。

如果用 `bindings = <&kp AT>, <&kp SLASH>`，长按时 ZMK 会让 `AT` **保持按下**，操作系统触发自动重复 → 输出 `@@@@@@@@`。

改用宏：

```dts
m_at: m_at {
    compatible = "zmk,behavior-macro";
    #binding-cells = <0>;
    wait-ms = <5>;
    tap-ms  = <5>;
    bindings = <&kp AT>;      // 宏的 tap 模式 = 按下再松开，只输出一次
};
```

宏在 tap 模式下是「按下→松开」，**只输出一个字符**，且不参与自动重复。空格的长按 Tab、停止的长按退出会话，都用了这个模式。

### 3.3 hold-tap 的参数占位规则

ZMK 的 hold-tap 固定是 `#binding-cells = <2>`，两个参数分别转发给 hold 和 tap 行为。

**零参数的行为（宏、tap-dance）要传 `0` 占位**：

```dts
&stop 0 0            // hold = m_quit(0参), tap = stop_td(0参)
&cmd 0 SLASH         // hold = m_at(0参),   tap = &kp(1参)
&spc_tab 0 SPACE     // hold = m_tab(0参),  tap = &kp(1参)
```

> 这是 ZMK 的硬性要求，漏了会编译失败。`tools/check_keymap.py` 会校验每个行为的参数个数。

### 3.4 flavor（裁决策略）怎么选

`flavor` 决定「按住期间又按了别的键」时判 hold 还是 tap。本项目按**误触代价**选：

| 键位 | flavor | 理由 |
|---|---|---|
| 空格 | `tap-preferred` | 最高频键。只有**刻意按住 300ms** 才出 Tab，正常打字绝不会误判 |
| 停止 | `tap-preferred` | 退出会话是破坏性操作，1200ms 长按才触发 |
| 语音 | `hold-preferred` | 「按住说话」是主用法，200ms 就进 push-to-talk |
| 访问等级 / 模型 / 命令行 | `balanced` | 折中，单击与长按都常用 |

### 3.5 空格键的特殊保护

空格是唯一一个「单击极高频、长按有副作用」的键，所以给了三重保护：

```dts
spc_tab: space_tab {
    flavor = "tap-preferred";        // 犹豫时判 tap
    tapping-term-ms = <300>;         // 要按住 300ms 才算长按
    quick-tap-ms = <150>;            // 150ms 内连按强制判 tap
    require-prior-idle-ms = <120>;   // 刚打完别的字后的 120ms 内禁用长按
};
```

## 4. 审批拨杆的处理

### 4.1 当前方案（v0.1）

拨杆接在矩阵 `(行1, 列6)`，绑定 `&kp F13`：

| 拨杆 | 键盘行为 |
|---|---|
| 拨到 ON | 持续按下 `F13` |
| 拨回 OFF | 释放 `F13` |

上位机监听 `F13` 的按下/释放事件，即可知道拨杆状态，从而决定是否自动审批。

**为什么这样够用**：拨杆是**两态**而非瞬时按键，`F13` 的「按下持续 / 释放」正好一一对应 ON / OFF，不需要额外的通信通道。

### 4.2 局限

这个方案只能**上报状态**，「检测到审批弹窗就自动应答」的逻辑全在上位机侧。这是刻意的——上位机才看得见终端输出。

### 4.3 更好的方案（后续）

PRD 6.3 定义了自定义 GATT 服务，可以把拨杆状态、权限档位、模型名做成特征值双向通信。这样：

- 键盘可以主动上报拨杆状态，不占用 HID 键码
- 上位机可以回写状态，驱动按键 RGB 显示当前档位（PRD 第 8 章）

代价是要写 ZMK 自定义 GATT 服务（C 代码），工作量明显大于当前方案。**建议先跑通 v0.1，确认产品可用后再做。**

按优先级：

| 优先级 | 事项 | 说明 |
|---|---|---|
| **P0** | **PCB 设计** | 当前只有外壳和定位板。PCB 决定引脚分配，需与 `claudepad.overlay` 对齐 |
| **P0** | **上位机程序** | 监听 `F13`/`F14`、读状态栏、执行复位与模型循环。**没有它，长按功能是空的** |
| **P1** | 编译验证 | 本文档的语法依据 ZMK 官方文档编写，但**未经实际编译**（本地无 Zephyr 工具链）。首次构建时请留意报错 |
| **P1** | 实测手感调参 | `tapping-term-ms` 等参数需上手实测后微调 |
| **P2** | 自定义 GATT 服务 | 实现状态回写与 RGB 指示 |
| **P2** | 每键 RGB 状态指示 | 依赖 P2 的 GATT 服务 |

### 5.1 关于「未经编译验证」

**这一点必须说清楚**：本固件配置是依据 ZMK 官方文档（shield 结构、hold-tap、tap-dance、macros 的语法）编写的，并做了静态一致性校验（`tools/check_keymap.py` 验证了键位数量、顺序、功能、参数个数）。

但**本地没有 Zephyr 工具链，所以没有真正编译过**。首次构建如果报错，大概率是：

1. `#include` 路径或 ZMK 版本差异（`west.yml` 锁在 `v0.1.0`）
2. 某个行为属性名在新版 ZMK 里改了
3. `F13` 键码名称（若报错可换成 `F14` 或其他）

## 6. 与其它交付物的关系

```
docs/PRD.md                  ← 产品定义（键位、手势、边界）
        │
        ├──→ cad/             ← 结构：外壳 / 定位板 / 键帽
        │       │
        │       └──→ 定位板轴孔数 ──┐
        │                            │
        └──→ firmware/       ← 固件：键位与手势
                │                    │
                └── tools/check_keymap.py ──→ 交叉校验两边是否一致
```

`tools/check_keymap.py` 是关键的「防漂移」工具：它把 `cad/lib/params.scad` 的键位表与 `claudepad.keymap` 的绑定逐项比对。改了任一边忘了另一边，脚本会立刻报错。
