# 审批拨杆技术验证报告

**版本**：v1.0
**日期**：2026-09-14
**验证对象**：PRD 9.3「待验证的技术路径：Claude Code Hooks」
**结论**：✅ **路线成立。审批拨杆可以用官方 hooks 机制实现，且优于原定的文本嗅探方案。**

---

## 0. 一句话结论

PRD 里标注的「整个产品最大的不确定性」已排除。

`PreToolUse` hook 返回 `permissionDecision: "allow"` **确实能跳过权限提示直接执行工具调用**；
而返回空则**不算批准**，工具调用继续走原生流程。

这两条语义恰好构成审批拨杆需要的开关行为：
**拨杆 ON → 返回 allow；拨杆 OFF → 返回空。** 不需要碰终端输出，不需要改权限配置。

## 1. 验证依据（官方文档的确切机制）

来源：Claude Code 官方 hooks 文档。

### 1.1 决策的返回方式

PreToolUse 用 `hookSpecificOutput` 对象表达决策，**不是**顶层 `decision` 字段：

```json
{
  "hookSpecificOutput": {
    "hookEventName": "PreToolUse",
    "permissionDecision": "allow",
    "permissionDecisionReason": "原因说明"
  }
}
```

`permissionDecision` 的四个取值：

| 取值 | 含义 |
|---|---|
| `allow` | **批准执行，跳过权限提示** |
| `deny` | 拒绝工具调用 |
| `ask` | 升级给用户询问 |
| `defer` | 延迟，稍后处理 |

### 1.2 关键细节：静默 ≠ 批准

官方原文：

> exit 0 且无输出 = hook 没有决定要报告，工具调用会继续走**正常权限流程**（仍可能提示用户）。hook 可以拒绝调用，但**保持沉默不会批准它**。

**这是整个方案能成立的核心。** 它意味着：

- 拨杆 OFF 时 hook 什么都不输出 → Claude Code 完全按原生行为走，用户的既有配置（`acceptEdits`、`plan` 等）不受任何影响
- 拨杆 ON 时 hook 输出 `allow` → 只有此时才介入

也就是说，**拨杆 OFF 时这个产品是「不存在」的**，不会给用户带来任何行为改变。这是最理想的产品形态。

### 1.3 hook 收到的输入

PreToolUse 的 stdin 是一个 JSON，含：

| 字段 | 用途 |
|---|---|
| `tool_name` | 工具名（`Bash` / `Edit` / `Write` / `AskUserQuestion` …） |
| `tool_input` | 工具参数对象（Bash 是 `command`，Edit 是 `file_path` 等） |
| `permission_mode` | 当前权限模式（`default` / `plan` / `acceptEdits` / `auto` / …） |
| `cwd` | 当前工作目录 |
| `session_id` | 会话标识 |
| `hook_event_name` | 事件名 |

有了 `tool_name` 和 `tool_input`，就能实现 PRD 4.4 要求的**危险命令分级**——这是文本嗅探做不到的。

### 1.4 退出码语义

| 退出码 | 行为 |
|---|---|
| `0` | 正常，解析 stdout 的 JSON |
| `2` | 阻止（对 PreToolUse 即阻止工具调用），stderr 反馈给 Claude |
| 其他非零 | 非阻止错误，执行继续 |

> 注意：**exit 1 不阻止**。要强制阻止必须用 exit 2。

### 1.5 超时

`command` / `http` 类型默认 **600 秒**，可在条目里用 `timeout` 字段自定义。

对本方案来说余量极大——我们只需要读一个文件。

## 2. 为什么这条路优于原定的「终端输出嗅探」

PRD 4.3 原本推荐「路线一：终端输出嗅探」，理由是「不碰配置、可逆」。hooks 路线现在看全面更优：

| 维度 | 终端输出嗅探 | Hooks（本方案） |
|---|---|---|
| **稳定性** | 依赖匹配 Claude Code 的文案，**改文案就失效** | 官方支持的稳定接口，不依赖文案 |
| **能否分级** | 只能看到终端文本，难结构化判断 | 直接拿到 `tool_name` + `tool_input`，能精确分级 |
| **是否侵入** | 要解析 TUI 重绘 / ANSI 转义，脆弱 | 官方扩展点，不侵入 |
| **误判风险** | 文本匹配天然会误判 | 结构化字段，无误判 |
| **可逆性** | 可逆 | 同样可逆（删掉 hook 配置即可） |
| **性能** | 需要持续读终端输出 | 每次工具调用一次判断，快路径 ~2ms |

**唯一代价**：需要在 `~/.claude/settings.json` 里加一条 hook 配置。但这比解析终端文本可靠得多，且随时可删。

## 3. 实测数据

### 3.1 延迟：command 模式 vs HTTP 模式

hooks 支持两种执行方式，实测差异巨大：

| 模式 | 中位延迟 | 最小 | 最大 |
|---|---|---|---|
| `command`（每次起进程） | **510 ms** | 489 ms | 600 ms |
| `http`（常驻进程应答） | **15 ms** | 2 ms | 28 ms |

**快了 34 倍。** 瓶颈是 Windows 上 Python 解释器的启动开销。

`command` 模式下每次工具调用都要多等半秒，不可接受。所以**最终方案采用 HTTP 模式**：
由一个常驻守护进程同时负责键盘监听和 hook 应答。

### 3.2 决策逻辑：31 个用例全部通过

测试台 `host/test_hook.py` 用 subprocess 直接喂 hook 各种输入，覆盖四类场景：

| 场景 | 用例数 | 结果 |
|---|---|---|
| 拨杆 OFF → 全部静默 | 3 | ✅ 不改变原生行为 |
| 拨杆 ON + 安全操作 → 批准 | 8 | ✅ 跳过权限提示 |
| 拨杆 ON + 危险操作 → 交回原生流程 | 17 | ✅ 不代批 |
| 拨杆 ON + 需用户判断 → 不代答 | 2 | ✅ |

危险操作覆盖：`rm -rf`、`rm -r`、`sudo`、`git push --force`、`git push -f`、
`git reset --hard`、`curl | sh`、`chmod 777`、`dd` 写盘、`shutdown`、fork bomb、
`npm publish`、Windows `del /s`、PowerShell `Remove-Item -Recurse -Force`。

受保护路径覆盖：`/etc/`、`~/.ssh/`、`~/.claude/settings.json`、`C:\Windows`。

### 3.3 访问令牌

守护进程监听在 `127.0.0.1`，理论上本机任何程序都能调用它。加了令牌校验：

| 请求 | 响应 | Claude Code 的处理 |
|---|---|---|
| 令牌正确 | HTTP 200 + 决策 | 按决策执行 |
| 令牌错误 | **HTTP 403** | 视为非阻塞错误 → 走原生流程 ✅ |
| 守护进程未运行 | 连接失败 | 视为非阻塞错误 → 走原生流程 ✅ |

## 4. 失效安全设计（重要）

自动批准是高风险功能，所以整个链路的失效方向必须是**「退化为正常询问」**，绝不能是「全部自动批准」。

实测确认了三层保障：

| 故障 | 结果 |
|---|---|
| 守护进程没跑 | 连接失败 → 非阻塞错误 → **原生流程**（正常询问） |
| 令牌不匹配 | 403 → 非阻塞错误 → **原生流程** |
| hook 脚本内部异常 | 捕获后返回空 → **原生流程** |
| 输入 JSON 解析失败 | 返回空 → **原生流程** |
| 状态文件损坏 / 不存在 | 视为拨杆 OFF → **原生流程** |

另外一条设计原则：**只升不降**。

hook 只会把结果升级为 `allow`，**从不返回 `ask` 或 `deny`**。危险命令一律静默放行给 Claude Code 原生流程判断。

这样做的好处：不会出现「用户本来在 `acceptEdits` 模式，结果因为拨杆 ON 反而被强制弹窗」这种反直觉行为。拨杆只做加法，不做减法。

## 5. 架构

```
   键盘拨杆拨到 ON
        │  BLE HID 发送 F13 按下
        ▼
   ┌─────────────────────────────────────┐
   │  claudepad_daemon.py（常驻）         │
   │  ├─ 键盘监听线程（pynput）           │
   │  │   捕捉 F13 按下/释放 → 写状态     │
   │  └─ HTTP 服务线程（127.0.0.1:8787）  │
   │      POST /hooks/pre-tool-use        │
   └──────────────┬──────────────────────┘
                  │ 读状态文件
                  ▼
        ~/.claudepad/approval.on
        （存在 = ON，不存在 = OFF）
                  ▲
                  │ 写入
        ┌─────────┴─────────┐
        │  Claude Code      │
        │  PreToolUse hook  │──── allow ──→ 跳过权限提示
        └───────────────────┘
```

**为什么状态用「文件存在性」而不是文件内容**：

hook 在每个工具调用上都会执行，快路径必须是单次 `stat` 系统调用。
`os.path.exists()` 正好是这个语义——拨杆 OFF 时（绝大多数情况）零解析开销。

**为什么守护进程同时干两件事**：

键盘监听和 hook 应答都要常驻，合并成一个进程省去额外部署。

**没有键盘也能测**：状态文件就是唯一接口，`switchctl.py on/off` 直接操作它。
所以整条链路现在就能验证，不必等硬件做出来。

## 6. 边界与限制

| 限制 | 说明 |
|---|---|
| **`AskUserQuestion` 永不代答** | 这是产品设计决定，也是官方明确不会自动批准的类型 |
| **需要常驻进程** | HTTP 模式必须保持守护进程运行。进程挂了只是退化为正常询问，不会误批 |
| **F13 可能被个别软件拦截** | 极罕见，若遇到可换 F14/F15（改固件 + 守护进程的 `VK_F13` 常量） |
| **状态是「本机」的** | 多台机器同时用需要各自跑守护进程 |
| **未在真实 Claude Code 上跑通** | 本机未安装 Claude Code CLI，验证是在协议层（按官方文档构造输入输出）完成的。首次接入真机时请按 §7 的步骤验证 |

> **关于最后一条**：这是本次验证最大的保留项。逻辑、协议格式、失效路径都已验证，
> 但「Claude Code 真的会按文档所述处理这个响应」这一步没有实测。
> 接入步骤见下节，5 分钟可以确认。

## 7. 接入真机的验证步骤

```bash
cd host

# 1. 逻辑自测（不需要 Claude Code）
python test_hook.py                     # 应输出「31 个用例全部通过」

# 2. 安装 hook（先预览，确认后加 --apply）
python install_hook.py
python install_hook.py --apply

# 3. 启动守护进程（保持运行）
python claudepad_daemon.py

# 4. 打开 Claude Code，做一件需要授权的事（比如让它新建一个文件）
#    —— 此时应该正常弹权限提示（拨杆 OFF）

# 5. 另开终端，手动打开拨杆
python switchctl.py on

# 6. 回到 Claude Code，再做一件需要授权的事
#    —— 此时应该**不再询问**，直接执行 ← 关键验证点

# 7. 关掉拨杆，确认恢复询问
python switchctl.py off
```

第 6 步不再询问 = 验证通过。
