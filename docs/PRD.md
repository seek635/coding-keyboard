# ClaudePad 产品需求文档（PRD）

**产品代号**：ClaudePad
**形态**：蓝牙（BLE）连接的编程专用实体小键盘
**版本**：v0.1（产品定义阶段）
**日期**：2026-09-14
**目标宿主**：Claude Code（CLI / 终端为主，兼容 IDE 终端）

---

## 1. 产品定位

### 1.1 一句话定义

一把为 AI 编程对话场景定制的蓝牙小键盘，把「与 Claude Code 对话、切换权限、审批操作」这些高频且必须用键盘完成的动作，从手指在 104 键上"找键"变成"按一个专属键"。

### 1.2 要解决的核心痛点

| 痛点 | 现状 | 本产品方案 |
|---|---|---|
| 方向键离手远 | 主键盘方向键在右侧，从打字区过去要移动整只手 | 方向键独立成一组，贴在主位区旁 |
| 权限模式切换靠记忆 | `Shift+Tab` 循环切，切到哪一档要靠状态栏文字确认 | 独立「访问等级键」，键帽丝印 + RGB 指示当前档位 |
| 审批要手动点 | 长任务中频繁弹出审批，每次都要移动手到回车 | 侧边物理拨杆，ON 时自动应答审批 |
| 语音输入要打命令 | 要先敲 `/voice` 再按住空格 | 独立语音键，按住即说 |
| 模型切换要打命令 | 敲 `/model` 或按 `P` 且要确认当前是哪个模型 | 独立模型切换键，长按进选择器 |

### 1.3 非目标（明确不做）

- ❌ 不做全尺寸键盘，不做打字主力键盘（本产品是**副键盘 / 快捷键外设**，定位为"左手边那块小板子"）
- ❌ 不做无线接收器版本（只做 BLE，不支持 2.4G 私有协议）
- ❌ 首版不追求跨软件通用（先聚焦 Claude Code，其他软件通过可编程键位兜底）
- ❌ 不做屏幕（成本与功耗不划算，状态反馈用 RGB + 键帽丝印）

## 2. 目标用户与使用场景

### 2.1 用户画像

**主用户**：使用 Claude Code 长时间跑任务的重度开发者。
典型特征是"双手不离键盘"，对快捷键有肌肉记忆，讨厌在终端里翻找功能，愿意为效率买专用硬件（类似买 Stream Deck 的人）。

### 2.2 核心场景

**场景 A — 长任务守望**
用户让 Claude 跑一个大规模重构，Claude 反复弹出「是否允许执行 rm」「是否允许写入配置文件」。用户此时在做别的事，用左手拇指把侧边拨杆拨到 ON，所有审批自动通过；任务结束拨回 OFF，恢复安全状态。

**场景 B — 权限梯度切换**
开始探索陌生代码库时切到 `plan`（只读）。确认思路后切到 `default` 手动审查。进入批量改文件的重复劳动时切到 `acceptEdits`。

**场景 C — 语音驱动**
构思到一半，不想打字，按住语音键口述需求，松开自动提交。

**场景 D — 打断与纠偏**
Claude 跑偏了，右手食指按下右上角停止键中断生成（单击 `Esc`），用方向键回看历史，改一句话按回车重发。

## 3. 按键清单与功能定义

### 3.1 物理按键总表

| # | 按键 | 类型 | 单击行为 | 长按行为 | 备注 |
|---|---|---|---|---|---|

| 2 | `↑` 上 | 单键 | 上方向 | 自动重复 | 方向键十字 |
| 3 | `↓` 下 | 单键 | 下方向 | 自动重复 | 方向键十字 |
| 4 | `←` 左 | 单键 | 左方向 | 自动重复 | 方向键十字 |
| 5 | `→` 右 | 单键 | 右方向 | 自动重复 | 方向键十字 |
| 6 | `语音` | 单键 | 按住说话，松开提交 | 双击切换启用 | 见 3.3，紧邻空格 |
| 7 | `模型` | 单键 | 唤起模型选择器 | 循环切换常用模型 | 见 3.4 |
| 8 | `空格` | **大键（跨 4 格）** | 空格 | 长按 = `Tab` 补全 | 独占一行，见 3.1.1 |

| 11 | `停止` | 单键 | 中断当前生成 / 停止任务 | — | 见 3.6 |
| 12 | `审批` 拨杆 | 侧边拨动开关 | OFF / ON 两态 | — | 见第 4 章，**核心差异点** |

> **本产品共 11 个物理按键 + 1 个侧边审批拨杆。** 其中回车与空格为大键（跨格），其余为单键。低频操作通过长按/双击手势承载，详见 3.6。

### 3.1.1 物理布局：三行五列

**主键区为三行 × 五列网格。** 方向键保留传统十字排列嵌入左侧，空格独占最底一行并横跨四格，回车跨两格位于第二行。

```
        ┌──────┬──────┬──────┬──────┬──────┐   ┌──────────┐
        │ 列1  │ 列2  │ 列3  │ 列4  │ 列5  │   │  侧边    │
┌───────┼──────┼──────┼──────┼──────┼──────┤   │ 审批拨杆 │
│ 行1   │访问等级│  ↑   │ 模型 │命令行│ 停止 │   │          │
├───────┼──────┼──────┼──────┼──────┴──────┤   │   OFF    │
│ 行2   │  ←   │  ↓   │  →   │   回车      │   │    ○     │
├───────┼──────┴──────┴──────┴──────┬──────┤   │          │
│ 行3   │          空格              │ 语音 │   │   ON     │
└───────┴───────────────────────────┴──────┘   │    ●     │
                                                └──────────┘
```

**格位分配表：**

| | 列1 | 列2 | 列3 | 列4 | 列5 |
|---|---|---|---|---|---|
| **行1** | 访问等级 | **↑** | 模型 | 命令行 | 停止 |
| **行2** | **←** | **↓** | **→** | **回车**（跨列4-5） | |
| **行3** | **空格**（跨列1-4） | | | | 语音 |

| 键位 | 位置 | 功能 | 备注 |
|---|---|---|---|
| 访问等级 | 列1·行1 | 循环切换 4 档 | RGB 指示，见第 5 章 |
| ↑ ← ↓ → | 列1-3·行1-2 | 方向键 | **传统十字排列**，↑ 居中，下方一排 ← ↓ → |
| 模型 | 列3·行1 | 单击唤起选择器，长按循环 | 见 3.4 |
| 命令行 | 列4·行1 | 输入 `/` | 见 3.5 |
| 停止 | 列5·行1 | 中断生成 / 停止任务 | 见 3.6 |
| 回车 | 列4-5·行2 | 发送输入 | **大键，跨 2 格** |
| 空格 | 列1-4·行3 | 空格 | **大键，跨 4 格，独占一行** |
| 语音 | 列5·行3 | 按住说话，双击启用 | 见 3.3，紧邻空格 |
| 审批拨杆 | 侧边（不占格位） | OFF / ON 两态 | 见第 4 章，**核心差异点** |

**布局原则：**

1. **方向键优先保形**——方向键是人类肌肉记忆最强的键群，**必须保留传统十字形状**（↑ 居中，下一排 ← ↓ →），不能为了布局整齐而拆散。这是本布局的最高优先级约束。
2. **大键承担高频操作**——空格独占一行横跨 4 格、回车跨 2 格，面积最大化，符合"最高频操作盲按容错最高"的原则。
3. **语音紧邻空格**——语音键位于底行最右，与空格同处底行。因为 Claude Code 的语音模式本身就是"按住空格说话"，两者相邻便于切换手势。
4. **停止键置于上排最右**——停止键位于行1 最右端。作为紧急操作键，位置需**醒目且易于定位**，同时远离空格避免误触（空格是最高频键，若停止紧邻则误停风险高）。
5. **侧边拨杆物理隔离**——不占网格格位，距离主键区最远，且是拨动而非按压，两种操作手感完全不同，避免误触。

> **几何说明**：方向键十字占据「列2·行1」的 ↑ 与「列1-3·行2」的 ← ↓ →，**十字形状完整无拆散**。↑ 两旁的两个格位（列1·行1、列3·行1）填入访问等级与模型——这是几何必然（十字最下排占满三格），也恰好是最合理的利用。

> **关于低频操作**：`Ctrl+R` 历史搜索、`/clear` 清空会话等操作**不占用物理键位**，由主键盘承担；`Tab` 补全、`@` 引用等通过长按/双击手势承载，详见 3.7。

### 3.2 键位设计原则

Claude Code 的实际操作点超过 20 个（权限模式 4 档、模型切换、语音、40+ 斜杠命令、历史回滚、中断、Tab 补全、文件引用 `@`……），而本产品只有 11 个物理键。

**本产品的键位设计原则：**

> **高频操作一键直达，低频操作手势复用，不增加物理键数。**

具体分工：

- **一键直达（11 个物理键）**：回车、方向键、语音、模型、空格、命令行、访问等级、停止 —— 这些是 AI 编程对话中每个会话都会反复用到的操作。
- **手势复用（长按 / 双击）**：`Shift+Enter` 换行、`@` 文件引用、`Tab` 补全、语音启用切换 —— 这些是次要操作，用同一批键的手势承载（详见 3.6）。
- **不纳入范围**：`Ctrl+R` 历史、`Ctrl+O` 详细输出、`/clear` 清空 —— 由主键盘承担，本键盘不做映射。

### 3.3 「语音输入键」行为定义

**关键依据**：Claude Code 的语音功能是 `/voice` 命令启用的"按住说话"（push-to-talk），默认绑定在**空格键**上。

因此本产品的语音键需要区分两种设计：

| 方案 | 行为 | 优劣 |
|---|---|---|
| **方案 A（推荐）** | 语音键模拟"按住空格说话"，前提是用户已开启 `/voice` | 无延迟，最接近原生体验；但需用户先启用语音功能 |
| **方案 B** | 语音键发送 `/voice` 命令启用功能，再按住说话 | 单键完成全流程；但首次按下会有一次命令往返延迟 |

**建议实现**：语音键**双击**发送 `/voice` 切换启用状态，**单击按住**执行 push-to-talk。同时键盘上保留独立空格键——当语音未启用时，空格就是普通空格，不冲突。

**位置**：语音键位于底行最右（列5·行3），与空格同处底行。因语音模式本身是"按住空格说话"，两者相邻使手势切换自然。

**状态反馈**：语音录制中，语音键 RGB 呼吸灯（红光）。

### 3.4 「模型切换键」行为定义

Claude Code 中模型切换可通过 `/model [model]` 命令或 `P` 键触发。

| 操作 | 行为 |
|---|---|
| 单击 | 发送 `/model` 并回车，唤起模型选择列表 |
| 长按（>800ms） | 在当前会话的常用模型间**循环切换**（快捷键实现，无菜单） |

**为什么加长按**：菜单选择需要方向键 + 回车三步，而循环切换只需一下。用户在 Opus / Sonnet 之间来回切时，长按是效率最高的路径。

**状态反馈**：模型键 RGB 颜色区分当前模型（如 Opus 紫、Sonnet 蓝）。**注意**：键盘无法感知 Claude Code 内部用了哪个模型，需要上位机配合读取状态后回写，详见 6.3。

### 3.5 「命令行键」行为定义

| 操作 | 行为 |
|---|---|
| 单击 | 输入 `/` 字符，唤起 Claude Code 的斜杠命令补全菜单 |
| 单击后继续键入 | 正常字母输入补全 |

**设计考量**：不做"N 个命令专属键"。斜杠命令有 40+ 个（`/clear` `/compact` `/resume` `/cost` `/context` `/diff` `/model` `/permissions` `/hooks` `/mcp` `/agents` `/voice` …），做专属键必然臃肿。正确做法是**一键唤起菜单 + 传统输入筛选**。

长按此键 = `@`，用于文件引用（见 3.6）。

### 3.6 「停止键」行为定义

**停止键是紧急操作键**，位于行1 最右格（列5·行1）。

| 操作 | 行为 | 说明 |
|---|---|---|
| **单击** | 发送 `Esc` | 中断当前生成 / 打断正在输出的回答 |
| **双击** | 发送 `Ctrl+C` | 强制取消当前任务（比 Esc 更彻底） |
| **长按（>1.5s）** | 发送 `Ctrl+C` 两次 | 退出当前会话（需谨慎，不轻易触发） |

**设计考量**：

1. **位置选择**——放在行1 最右端。该位置在键盘右上角，是**视线与手指都容易定位的显著位置**；同时远离空格（最高频键），避免误触导致意外中断。相比放在空格旁边，此方案以"降低误触风险"优先。
2. **为什么需要物理键**——停止是**唯一的"紧急中断"操作**，用户需要在发现 AI 跑偏的**第一瞬间**按下。如果还要移手到主键盘找 `Esc`，那几秒的延迟足以让 AI 完成一连串错误操作。
3. **单击 = Esc 而非 Ctrl+C**——`Esc` 只中断当前生成但保留会话上下文，是更常见的需求；`Ctrl+C` 会取消整个任务，破坏性更强，所以放在双击（需要刻意操作）。
4. **键帽设计**——建议用**凸起或异色键帽**，便于在盲操时通过触感快速定位，无需低头寻找。

**状态反馈**：按下后键盘短暂显示橙光确认（区别于审批拨杆的红色警示）。

### 3.7 低频操作的处理方式（手势复用）

除停止键外，产品不再增加物理键。以下低频操作通过**手势复用**承载：

| 承载方式 | 映射 | 用途 |
|---|---|---|
| 双击「语音」 | `/voice` | 切换语音功能启用状态 |
| 长按「模型」 | 循环切换模型 | 免菜单快速切换 |
| 长按「访问等级」 | 复位到 `default` | 一键回到安全档位 |
| 双击「回车」 | `Shift+Enter` | 输入框内换行 |
| 长按「命令行」 | `@` | 文件引用 |
| 长按「空格」 | `Tab` | 自动补全 |

**其余更低频操作**（`Ctrl+R` 历史搜索、`Ctrl+O` 详细输出、`/clear` 清空会话）**由主键盘承担**，不纳入本产品范围。

## 4. 「侧边自动审批按钮」——核心差异点

### 4.1 功能定义

**拨杆式物理开关，两态：**

- **OFF**：键盘不干预任何审批流程，一切按 Claude Code 原生行为走
- **ON**：键盘进入**监视模式**，当检测到 Claude Code 弹出审批申请时，**自动代替用户发送"同意"**

### 4.2 与「访问等级键」的职责边界（重要）

这两者**不是重复功能**，而是两个层次：

| 维度 | 访问等级键 | 审批拨杆 |
|---|---|---|
| **作用对象** | 规则本身 | 已经发生的申请 |
| **时机** | 事前——设定"什么样的操作才要问我" | 事中——模型已经在等待答复 |
| **持续性** | 切换后持续生效，直到下次切换 | 拨杆在 ON 期间生效 |
| **本质** | 修改 Claude Code 的 `permissions.defaultMode` | 监听审批事件并自动应答 |
| **粒度** | 按操作类型分级（只读 / 编辑 / 命令 / 全部） | 全通过，不做类型区分 |

**举例说明差异**：
- 用**访问等级键**切到 `acceptEdits`：文件编辑不再询问，但 `rm -rf` 这类命令**仍会**询问。
- 把**审批拨杆**拨到 ON：连 `rm -rf` 的询问也会被自动同意。

> ⚠️ 因此审批拨杆是**高风险开关**，必须配套强视觉警示，见 4.5。

### 4.3 实现机制（两种技术路线）

**路线一：终端输出嗅探（推荐，纯键盘可实现）**

键盘通过 BLE HID 与主机相连，同时上位机（或键盘固件的辅助通道）监视 Claude Code 的终端输出。

```
Claude Code 输出审批提示
        ↓
检测到特征串（如 "Do you want to proceed?" / "1. Yes" / "❯ 1. Yes"）
        ↓
拨杆 = ON ？
   ├─ 否 → 不动作
   └─ 是 → 向终端注入「回车」或「Y」+ 回车
```

**优点**：不碰 Claude Code 配置，不改变权限模型，可逆、可控。
**缺点**：依赖终端输出特征匹配，Claude Code 改文案可能失效。

**路线二：直接改写权限配置**

拨杆 ON 时，由上位机把 `~/.claude/settings.json` 的 `permissions.defaultMode` 改为 `acceptEdits`（或启动 Claude Code 时加 `--permission-mode`）。拨杆 OFF 时改回。

**优点**：不依赖文案匹配，稳定。
**缺点**：粒度粗、有落盘副作用、`auto`/`bypassPermissions` 在项目级 settings 中不生效（必须在用户级），且修改配置文件的行为本身可能被其他工具感知。

**建议**：**首版走路线一**，把路线二作为高级选项。理由：路线一不改变用户环境、行为完全可逆、不会因为改配置文件导致用户在别处的困惑。

### 4.4 自动应答的"安全默认值"

不是所有审批都该自动同意。建议按以下分级：

| 审批类型 | 拨杆 ON 时行为 |
|---|---|
| 文件读取 | 自动同意 |
| 文件编辑 / 创建 | 自动同意 |
| 常规 shell 命令（`ls` `git status` `npm test`） | 自动同意 |
| 危险命令（`rm -rf`、`sudo`、写入受保护路径、`git push --force`） | **默认不自动同意**，改为高亮闪烁提示，需用户按键确认 |
| `AskUserQuestion`（需要用户交互的工具） | **永不自动应答**（Claude Code 本身也不会自动批准这类） |

**注意**：Claude Code 官方明确即使 `bypassPermissions` 模式下也有不自动批准的操作（显式 `ask` 规则、`AskUserQuestion`、关键路径的 `rm`/`rmdir`、跨会话消息保护等）。键盘的自动审批应当**尊重这些不可绕过的边界**，不做"强行注入"。

### 4.5 安全设计（必须项）

| 措施 | 说明 |
|---|---|
| 拨杆位置醒目 | 放在键盘**侧边**，用大面积红色拨杆，与按键物理隔离，防误触 |
| 状态灯常亮 | ON 时键盘整体指示灯变红/橙，或拨杆旁高亮 LED，余光可见 |
| 启动蜂鸣 | 拨到 ON 时蜂鸣一声，拨回 OFF 时蜂鸣两声 |
| 自动回位（可选） | 可配置"ON 状态 30 分钟无操作自动回 OFF" |
| 危险命令白名单 | 见 4.4，危险命令不自动通过 |
| 二次确认（可选） | 高安全模式：拨杆 ON 后首次自动审批前需长按确认一次 |

## 5. 访问等级键——4 档定义

依据 Claude Code 官方权限模式文档，键盘的 4 档映射为 `Shift+Tab` 循环内的四个常用档位：

| 档位 | Claude Code 配置值 | UI 标签 | 含义 | 键帽 RGB |
|---|---|---|---|---|
| ① | `plan` | Plan | 只读研究，不做任何修改，先出计划 | 蓝 |
| ② | `default` | Manual | 每个编辑和命令都要确认（最安全） | 绿 |
| ③ | `acceptEdits` | Edit automatically | 自动接受文件编辑，命令仍询问 | 黄 |
| ④ | `auto` | Auto | 一切自动，后台分类器安全检查 | 橙 |

### 5.1 为什么是这个顺序

按**放权程度递增**排序：只读 → 手动 → 自动改文件 → 全自动。用户按住一键循环时，心里的预期是"越来越放手"，而不是官方那个 `default → acceptEdits → plan` 的顺序（那个顺序对新手不直观）。

### 5.2 两个未进入 4 档的模式

| 模式 | 为什么不做进循环 |
|---|---|
| `dontAsk` | 官方明确规定**永不进入 Shift+Tab 循环**，只能靠 `--permission-mode dontAsk` 启动。键盘无法在会话中切到它 |
| `bypassPermissions` | 官方规定必须先以该模式启动才能进入循环，且仅限隔离容器/虚拟机。放进常规循环太危险 |

**处理方式**：这两个模式**不纳入键盘映射**。用户如需要，直接在终端以启动参数指定（`claude --permission-mode dontAsk`）。

### 5.3 状态反馈机制

**核心难题**：键盘不知道 Claude Code 当前处于哪一档。

**解决方案优先级**：

1. **被动侦测（推荐）**：上位机读取终端状态栏文本（如 `⏸ plan mode on`、`⏵⏵ accept edits on`、`⏵⏵ auto mode on`），解析后回写给键盘。这是最准确的方式。
2. **主动记账**：键盘自己记住"我按了几次"，据此推算档位。缺点：用户在键盘外按 `Shift+Tab`、或 Claude Code 自己切换（如 plan 批准后进入 auto）时，键盘的记账会错位。**此方案单独使用不可靠，只作为上位机不可用时的降级方案。**
3. **混合**：优先被动侦测；侦测不到时用主动记账；两者冲突时以被动侦测为准。

### 5.4 长按复位

长按访问等级键 >1.5 秒 → 复位到 `default`。

**理由**：用户在慌乱中最需要的是"立刻回到安全状态"，而不是循环按三下。一键回到手动审查是最符合直觉的紧急出口。

## 6. 通信与协议设计

### 6.1 传输层

| 项目 | 方案 |
|---|---|
| 无线 | BLE 5.0+（低功耗，兼容性好） |
| 标准通道 | HID over GATT（HOGP）——用于发送按键，无需驱动、免安装 |
| 辅助通道 | BLE 自定义 GATT 服务——用于键盘 ↔ 上位机双向通信（状态回写、配置下发） |

**为什么需要双通道**：HID 只能单向"发按键"，无法接收"当前权限档位""当前模型名"这类状态。自定义 GATT 服务提供回传能力，才能实现 5.3 的 LED 状态指示。

### 6.2 HID 按键映射表

| 物理键 | 发送的 HID 报告 |
|---|---|
| Enter | `Enter` |
| ↑ ↓ ← → | 对应方向键 |
| 空格 | `Space` |
| 语音（按住） | `Space`（长按，配合 `/voice` 已启用） |
| 语音（双击） | `/voice` 字符序列 + `Enter` |
| 模型（单击） | `/model` 字符序列 + `Enter` |
| 模型（长按） | 由上位机执行循环切换（发自定义事件，不发按键） |
| 命令行 | `/` |
| 命令行（长按） | `@` |
| 空格（长按） | `Tab` |
| 回车（双击） | `Shift+Enter` |
| 停止（单击） | `Esc` |
| 停止（双击） | `Ctrl+C` |
| 访问等级 | `Shift+Tab` |
| 访问等级（长按） | 连续发送 `Shift+Tab` 直至回落 default，或发自定义事件由上位机处理 |
| 审批拨杆 ON | 自定义 HID Consumer Control 事件 / 自定义 GATT 特征值 |

### 6.3 自定义 GATT 服务草案

| 特征值 | 方向 | 用途 |
|---|---|---|
| `PermissionMode` | 主机 → 键盘 | 回写当前权限档位（plan/default/acceptEdits/auto），驱动 RGB |
| `ModelState` | 主机 → 键盘 | 回写当前模型名，驱动模型键颜色 |
| `ApprovalSwitch` | 键盘 → 主机 | 上报拨杆状态变化（ON/OFF） |
| `ApprovalEvent` | 主机 → 键盘 | 通知"当前有审批弹出"，键盘可据此闪烁提示 |
| `KeyConfig` | 主机 → 键盘 | 下发键位重映射配置（可编程键位） |
| `BatteryLevel` | 键盘 → 主机 | 电量上报 |

## 7. 硬件选型建议

### 7.1 主控芯片

| 方案 | 优势 | 劣势 | 推荐度 |
|---|---|---|---|
| **nRF52840** | 蓝牙协议栈成熟、低功耗顶级、ZMK 原生支持、社区资源多 | 单价略高 | ⭐⭐⭐⭐⭐ |
| **ESP32-C3 / S3** | 便宜、生态大、可跑更复杂逻辑 | 功耗高于 nRF | ⭐⭐⭐ |
| **nRF52832** | 便宜、够用 | 内存小，扩展受限 | ⭐⭐⭐ |

**建议**：**nRF52840**。若采用现成的开源方案（如 nice!nano 兼容板），可直接省掉射频设计这一大块工作。

### 7.2 固件方案

| 方案 | 说明 | 推荐度 |
|---|---|---|
| **ZMK** | 现代开源键盘固件，BLE 原生、配置化、低功耗好、支持自定义 GATT 扩展 | ⭐⭐⭐⭐⭐ |
| QMK + 蓝牙 | QMK 蓝牙支持弱，不推荐 | ⭐⭐ |
| 裸机自研 | 完全可控，但蓝牙协议栈工作量巨大 | ⭐ |

**建议**：**ZMK**。它是目前 BLE 键盘的事实标准，支持 `zmk,behavior-*` 自定义行为和扩展，且键位映射用 devicetree 描述，改键位不用改代码。

### 7.3 其他部件

| 部件 | 建议 |
|---|---|
| 轴体 | 建议矮轴（如凯华 Choc），键程短、适合快捷键高频敲击、键盘可做薄 |
| 方向键 | 可用五向摇杆（joystick）替代四个独立键，进一步省空间 |
| 审批拨杆 | 推荐 **SPDT 拨动开关**（手感明确、状态可见），不推荐自复位按钮 |
| RGB | 每键独立 WS2812，用于权限档位 / 模型 / 语音状态指示 |
| 电池 | 500–800mAh 锂电池，BLE 低功耗下续航可达数周 |
| 输入电压 | USB-C 充电 + 有线模式切换（有线时可省电、可刷固件） |

## 9. 边界条件与风险

### 9.1 技术风险

| 风险 | 影响 | 缓解措施 |
|---|---|---|
| Claude Code 更新改变审批文案 | 输出嗅探失效，自动审批不工作 | 特征匹配做成可配置规则集；提供"最近未匹配的审批提示"日志供用户补充规则 |
| 终端渲染复杂（TUI 重绘、ANSI 转义） | 文本嗅探解析困难 | 优先解析结构化部分；或走 Claude Code hooks 机制（见 9.3） |
| 键盘无法感知真实权限档位 | LED 显示错误，用户误判 | 以上位机被动侦测为主，主动记账仅作降级 |
| BLE HID 延迟 | 快捷键响应不跟手 | 选低延迟连接间隔（7.5ms）；有线模式兜底 |
| 自动审批被误认为"键盘帮我做了危险操作" | 用户信任受损 | 强制视觉警示 + 危险命令白名单 + 完整操作日志 |

### 9.2 合规与信任风险

- **自动审批本质上是代替用户做安全决策**。必须让用户在开启时明确知晓风险，建议首次拨到 ON 时在屏幕上显示一次性风险提示。
- 建议**默认关闭**自动审批功能，由用户在设置中主动开启。
- 建议保留**审批操作日志**（时间、命令内容、是否自动通过），便于事后审计。

### 9.3 待验证的技术路径：Claude Code Hooks

Claude Code 支持 **hooks** 机制（`PreToolUse` / `PostToolUse` 等），可以在工具调用前执行自定义脚本并返回决策。相比终端文本嗅探，hooks 是**官方支持的稳定接口**：

```
模型发起工具调用
        ↓
PreToolUse hook 被触发
        ↓
hook 脚本读取键盘拨杆状态（通过本地 socket / 文件 / GATT）
        ↓
拨杆 ON → 返回 allow；拨杆 OFF → 返回 ask（走原生流程）
```

**这是比文本嗅探更优的方案，建议在技术验证阶段优先尝试。** 好处：
- 不依赖终端输出格式，Claude Code 升级不易失效
- 决策在官方提供的扩展点上做，不侵入
- 可以拿到结构化的工具名和参数，能实现 4.4 的危险命令分级

**待办**：验证 hooks 能否实时读取外部状态（键盘拨杆），以及 hook 返回 `allow` 是否能跳过审批提示。

## 附录 A：Claude Code 权限模式速查（依据官方文档）

| 配置值 | UI 标签 | 免询问范围 | 状态栏显示 | 是否在 Shift+Tab 循环 |
|---|---|---|---|---|
| `default` | Manual | 仅读取 | `⏸ manual mode on` | ✅ |
| `acceptEdits` | Edit automatically | 读取 + 文件编辑 + 常见文件命令 | `⏵⏵ accept edits on` | ✅ |
| `plan` | Plan | 读取 + 分类器批准的命令 | `⏸ plan mode on` | ✅ |
| `auto` | Auto | 一切（分类器后台审查） | `⏵⏵ auto mode on` | ✅（需可用） |
| `dontAsk` | don't ask | 读取 + 预批准工具，其余拒绝 | `⏵⏵ don't ask on` | ❌ 永不出现 |

## 附录 B：任何权限模式下都不会自动批准的操作

即使在 `bypassPermissions` 下，以下操作仍不会被自动批准（键盘的自动审批也应尊重这些边界）：

- 匹配显式 `ask` 规则的工具
- 组织设置为 `ask` 的连接器工具
- 需要用户交互的工具（`AskUserQuestion`、`requiresUserInteraction` 的 MCP 工具）
- 针对关键路径的 `rm` / `rmdir`
- 跨会话消息传递保护
- 开启 `permissions.blockReadsOutsideWorkingDirectories` 时的工作目录外读取
